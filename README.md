# Leng — переводчик, который учит

Персональный инструмент для одного пользователя: переводчик, который превращает каждое «покажи перевод» в сигнал о пробеле в знании. Выделяешь английский текст в любом приложении, дважды нажимаешь Cmd+C — мгновенно появляется плавающий HUD с переводом. Каждый запрос сохраняется в базу и накапливается в сигналы для обучения (словарный трекинг, разборы, утренний урок в Telegram — по мере развития версий).

Это личный проект: один пользователь, никаких регистраций, облака и телеметрии. Весь текст запросов уходит только на собственный LLM-эндпоинт и в собственную базу.

Документация:

- **PROJECT_CONCEPT.md** — продуктовое видение: что это, зачем и как должно вести себя.
- **PROJECT.md** — техническая спецификация: архитектура, модель данных, API, тестирование.
- **PIPELINE.md** — процесс разработки.

## Архитектура

Три части:

1. **Десктопный клиент (Tauri 2)** — macOS и Windows. Трей-приложение: наблюдает двойное Cmd+C (Ctrl+C на Windows), читает буфер обмена, показывает плавающий HUD с вкладками «Перевод» и «Разбор». Клиент тонкий — всю семантику считает бэкенд.
2. **Бэкенд (Python 3.12 + FastAPI) в одном Docker-контейнере.** HTTP API `/v1`, классификация запросов, перевод, словарный трекинг. База — SQLite в примонтированной папке `/data`, без ORM. Telegram-бот — позже, в том же контейнере.
3. **LLM — один OpenAI-совместимый эндпоинт** (Ollama / llama.cpp / vLLM). Адрес, имя модели и ключ задаются в конфиге. Эндпоинт обязан поддерживать режим `response_format: {"type": "json_object"}`. Все вызовы моделей идут из бэкенда; клиент моделей не вызывает.

Ключевое следствие: клиент зависит от бэкенда — нет контейнера, нет перевода. HUD честно сообщает «бэкенд недоступен», не крутясь бесконечно.

## Состав репозитория

```
leng/
  backend/            # FastAPI-бэкенд: app/, migrations/, prompts/, tests/
  client/
    src/              # UI HUD (vanilla HTML/CSS/JS)
    core/             # крейт leng-core: логика клиента + бинарник leng-cli
    src-tauri/        # Tauri-обёртка: триггер, окна, буфер
  scripts/            # test.sh, golden.sh — гейты качества
  docker-compose.yml  # боевой бэкенд (+ fake-llm в test-профиле)
  Dockerfile          # образ бэкенда (python:3.12-slim + uv)
```

## Развёртывание, шаг за шагом

### 0. Что нужно заранее

- Docker Desktop (macOS/Windows) или dockerd с Docker Compose v2 — для бэкенда.
- Rust-тулчейн (`rustup`, стабильный канал) — для клиента. На macOS также Xcode Command Line Tools (`xcode-select --install`); на Windows — MSVC Build Tools и WebView2.
- Уже работающий LLM-эндпоинт с OpenAI-совместимым API и JSON-режимом; его адрес и ключ вводятся в `.env` на шаге 2.

### 1. Получить код

```bash
git clone <адрес-репозитория> leng
cd leng
```

### 2. Бэкенд: конфигурация

Скопировать шаблон и заполнить:

```bash
cp .env.example .env
```

Обязательные значения:

- **`LENG_API_TOKEN`** — токен, который клиент передаёт в заголовке `X-Api-Token` на каждый запрос. Это защита от случайного соседа по локальной сети, а не корпоративная безопасность. Сгенерировать, например: `openssl rand -hex 32`.
- **`LENG_LLM_BASE_URL`** — базовый URL LLM-эндпоинта; клиент бэкенда добавляет к нему `/v1/chat/completions`. Пример: `http://host.docker.internal:11434` для Ollama на той же машине (бэкенд живёт в контейнере, поэтому `localhost` в него не попадает; в Docker Desktop `host.docker.internal` работает из коробки, в Linux добавь сервису `backend` в `docker-compose.yml` строку `extra_hosts: ["host.docker.internal:host-gateway"]`).
- **`LENG_LLM_API_KEY`** — ключ, отправляемый как Bearer-токен в LLM. Ollama игнорирует значение — подойдёт любая непустая строка.
- **`LENG_DB_PATH`** — путь к файлу SQLite; требуется переменной конфига, но внутри контейнера compose принудительно задаёт `/data/leng.db`, так что значение в `.env` имеет смысл только для запуска без Docker.

Опциональные (значения по умолчанию закомментированы в `.env.example`):

- `LENG_LLM_MODEL` — имя модели (по умолчанию `glm5.3-flash:claude`).
- `LENG_LLM_TIMEOUT_S` — таймаут запроса к LLM в секундах (по умолчанию 10).
- `LENG_PORT` — хост-порт бэкенда (по умолчанию 28080).
- `LENG_DATA_DIR` — хост-папка, монтируемая в контейнер как `/data` (по умолчанию `./data`).

Файл `.env` уже в `.gitignore` — не коммить его и не переноси между машинами: на новой машине заполни заново.

### 3. Бэкенд: сборка и запуск

```bash
docker compose up -d --build
```

В первый раз соберётся образ; далее та же команда переезжает на обновлённый код. Внутри контейнера: база — `/data/leng.db`, порт — 8000, наружу — `LENG_PORT` (по умолчанию 28080).

### 4. Проверить, что бэкенд жив

Health-эндпоинт не требует токена:

```bash
curl http://localhost:28080/v1/health
```

Ожидается ответ `200`. Docker сам следит за здоровьем контейнера (healthcheck встроен в compose).

Затем проверить связку с LLM реальным запросом (токен — твой `LENG_API_TOKEN`):

```bash
curl -s http://localhost:28080/v1/query \
  -H "Content-Type: application/json" \
  -H "X-Api-Token: $LENG_API_TOKEN" \
  -d '{"raw_text": "hello", "source": {"app": "curl", "title": "", "url": ""}, "client": "smoke"}'
```

Ожидается JSON с `query_id`, `kind` и переводом. Ошибка `502` — бэкенд жив, но LLM не отвечает или возвращает не тот формат: смотри `docker compose logs backend`.

### 5. Клиент: конфигурация

Клиент конфигурируется переменными окружения на момент запуска:

- **`LENG_BACKEND_URL`** — URL бэкенда, например `http://localhost:28080`.
- **`LENG_API_TOKEN`** — тот же токен, что и в `.env` бэкенда.

### 6. Клиент: сборка

На dev-машине (сначала macOS — порядок платформ по роадмапу):

```bash
cd client/src-tauri
cargo build
```

Готовый бинарник: `client/src-tauri/target/debug/leng`. (Финальная сборка для личного инструмента не требует подписи и нотаризации; если нужен релиз-бинарник — `cargo build --release`, продукт будет в `target/release/leng`.)

### 7. Клиент: разрешение macOS

Наблюдение двойного Cmd+C требует прав Accessibility — иначе горячее нажатие не увидит вторую копию:

1. Запустить клиент в первый раз — он предложит экран онбординга с детектором состояния.
2. System Settings → Privacy & Security → Accessibility → включить `leng`.

Разрешение достаточно выдать по одному пути: `leng` — единый процесс, отдельного helper-приложения нет.

### 8. Запустить клиент

```bash
cd client/src-tauri
LENG_BACKEND_URL=http://localhost:28080 \
LENG_API_TOKEN=<твой-токен> \
  target/debug/leng
```

Приложение появляется в трее. Автозапуск включается в самом приложении (`tauri-plugin-autostart`).

### 9. Проверить петлю end-to-end

1. Открой в Chrome любую англоязычную страницу.
2. Выдели слово и дважды быстро нажми **Cmd+C** (окно-детектор ~500 мс).
3. У курсора появляется HUD со спиннером, затем перевод. Повторные переводы того же слова приходят из кэша мгновенно.
4. При выключенном контейнере HUD показывает «бэкенд недоступен» и закрывается.

Для проверки без GUI есть headless-путь тем же клиентским пайплайном:

```bash
cd client
cargo run -p leng-core --bin leng-cli -- trigger \
  --text "hello" --base-url http://localhost:28080 --token <твой-токен>
```

### 10. Обновление

```bash
git pull
docker compose up -d --build   # на машине с бэкендом
```

Миграции применяются автоматически при старте бэкенда. При обновлении клиента — снова шаг 6.

### 11. Данные и бэкап

- Всё состояние — один SQLite-файл в папке `data/` (том `LENG_DATA_DIR` → `/data`).
- Бэкап — копия папки `/data`. SQLite WAL включён; перенос на другую машину = поднять контейнер там же и указать ту же папку.
- «Перенос» не переносит секреты: токен и ключ LLM живут в `.env` и на новую машину вводятся заново.

## Тесты

Один гейт для приёмки изменений:

```bash
./scripts/test.sh
```

Стадии: pytest бэкенда → ruff → mypy --strict → cargo fmt/clippy/test на клиенте. Ненулевой выход — коммить нельзя.

Golden-path e2e (сборка образа, compose-профиль test с fake-LLM, word-запрос, проверка базы) — отдельно, hermetic:

```bash
./scripts/golden.sh
```
