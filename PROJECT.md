# Leng — техническая спецификация

Продуктовое видение и поведение продукта — источник истины: **PROJECT_CONCEPT.md**.
Этот документ описывает, *как* оно устроено технически. Продуктовые споры решаются по PROJECT_CONCEPT.md, технические — по этому документу. Если конфликт — PROJECT_CONCEPT.md сильнее, а PROJECT.md правится.

Пользователь продукта один. Многопользовательность, облако, публичные регистрации — вне проекта навсегда.

## 1. Архитектура

Три части:

1. **Десктопный клиент (Tauri)** — macOS и Windows. Трей-приложение: перехват двойного Cmd+C/Ctrl+C, чтение буфера обмена, плавающий HUD-оверлей с двумя вкладками («Перевод», «Разбор»). Клиент тонкий: он не решает, что это за запрос и что попадёт в уроки, — всю семантику считает бэкенд.
2. **Бэкенд (Python/FastAPI) в одном Docker-контейнере.** HTTP API для клиента, движок сигналов (классификация запросов, словарный трекинг, приоритеты), позже — планировщик повторений и Telegram-бот. База — SQLite-файл в примонтированной папке (`/data`). Запускаться может где угодно; расположение ничего не меняет.
3. **LLM — один Ollama-совместимый API.** Адрес и имя модели в конфиге. Все вызовы моделей идут из бэкенда; клиент моделей не вызывает. Один контракт на всё: перевод, разбор, извлечение кандидатов, генерация уроков, проверка писем.

Ключевое следствие: клиент зависит от доступности бэкенда — нет контейнера, нет перевода. HUD обязан честно сообщать «бэкенд недоступен» (зафиксированный таймаут, см. §9), а не крутиться бесконечно.

## 2. Стек

**Решение** (выбрано в обсуждении со мной; в спорных местах подписано «Решение»):

- **Клиент**: Tauri 2 — один код на обе ОС, маленький бинарник и память (HUD висит поверх всего — это важно), плагины: `global-shortcut`/системные хуки для триггера, `clipboard-manager` для чтения буфера. UI вкладок — ванильный HTML/CSS/JS в окне webview, без фреймворка: две вкладки не стоят React.
- **Бэкенд**: Python 3.12+, FastAPI, `uvicorn` внутри контейнера. Telegram-часть — `aiogram` (long polling: не требует публичного endpoint и не открывает наружу лишних портов).
- **База**: SQLite. **Решение**: без ORM — стандартный модуль `sqlite3` + нумерованные SQL-миграции в `backend/migrations/`, применяемые при старте. Схема простая и полностью под нашим контролем; ORM не даёт здесь выигрыша.
- **LLM-клиент**: OpenAI-совместимый endpoint (`/v1/chat/completions`) — Ollama его поддерживает, а заодно работает llama.cpp / vLLM. Endpoint обязан поддерживать поле `response_format: {"type": "json_object"}` (JSON-режим) — обязательное требование к любому провайдеру, а не опция; сервер, который на него отвечает 400, не считается OpenAI-совместимым. Формат ответа задаёт системный промт (схема — `app/llm/base.py`); если модель вернула не ту структуру, это ошибка: один ретрай с уточнением, дальше `LLMError` → HTTP 502 клиенту, не попытка починить ответ. Ollama живёт локально на одной из машин пользователя, не на внешнем хостинге. Модель по умолчанию: `glm5.3-flash:claude` (точная строка — в конфиге).
- **Контейнер**: `docker compose up -d`, том `./data:/data`, конфиг через `.env`.

## 3. Роадмап (границы версий)

### MVP-1 — перевод и накопление (первая живая версия)

Работает петля «выделил → двойной Cmd+C → HUD → перевод», всё сохраняется в базу. Telegram-уроков нет — данные копятся.

- Клиент: триггер двойной копии, HUD, вкладка «Перевод», ошибка «бэкенд недоступен». **Порядок платформ: сначала macOS** (dev-машина, вся механика выверяется на ней), затем Windows — пишется поверх уже работающей macOS-логики и вручную отлаживается на второй машине; обе платформы входят в MVP-1.
- Бэкенд: приём запросов, мгновенный перевод через LLM, классификация «слово/фраза/предложение/абзац» (см. §6), сохранение запроса со всеми полями (§5), словарные карточки для слов и фраз.
- Кэш словаря: повтор слова возвращается из базы мгновенно, без LLM.
- Таба «Разбор», мягкий HUD, кандидаты — НЕ в MVP-1.

Свойство, ради которого так: сырые запросы лежат с первого дня, значит классификацию и «Разбор» можно достроить позже и **заполнить задним числом** по уже накопленной базе — ничего не потеряно между MVP-1 и MVP-2.

### MVP-2 — сигналы и «Разбор»

- Вкладка «Разбор» в HUD: разбор предложения по блокам с ролями и связками, грамматическая связка на правиле из 1–3 предложений, действие «показать перевод» (перевод спрятан до нажатия — само-проверка), действие «знаю это».
- Мягкий HUD для повторных слов: сначала прошлый контекст + просьба вспомнить, перевод — вторым действием.
- Извлечение кандидатов из разобранных предложений; кандидат становится карточкой только после подтверждения в «Разборе».
- Грамматическая карта: темы, встретившиеся в разборах, с весами и ссылками на предложения.
- Маршрутизация: грамматически нагруженные чанки («should have done» и подобные) → «конструкция дня», не словарный трек.
- «Упрямые» слова: повторный перевод одного слова повышает приоритет; потолок и выходы по правилам PROJECT_CONCEPT.

### MVP-3 — утренний урок в Telegram

- Telegram-бот в том же контейнере, `aiogram`, long polling, один пользователь, токен в env.
- Три блока из PROJECT_CONCEPT: слова (включая продуктивные, обратные карточки), конструкция дня, письмо (раз в 2–3 дня).
- Планировщик интервальных повторений: интервалы растут, «знаю это» выводит после одного контрольного возврата, backlog для пустых дней, пропуск до 7 дней, обзорные недели раз в 2–3 недели.
- Время урока и таймзона — в конфиге.
- Грамматическая тема подробнее — по кнопке в боте, на материале собственных запросов.

### MVP-4 — замер понимания

Периодический замер (раз в 1–2 недели): незнакомый фрагмент вне запросов пользователя, «прочитай и одной фразой напиши, о чём это», AI-сравнение «как написал я» с ответом. Единственный счётчик прогресса.

## 4. Захват: двойной Cmd+C

Механика копирует Context Reverso:

1. Пользователь выделяет текст в любом приложении и дважды быстро нажимает Cmd+C (Win: Ctrl+C). Первое нажатие копирует выделение в буфер — его выполняет система, никто ничего не перехватывает.
2. Клиент **наблюдает** нажатия, не «съедая» их: macOS — `NSEvent.addGlobalEventMonitor`-подобный observe-only event tap (Carbon `AddGlobalMonitorsForEvents`); Windows — `SetWindowsHookEx(WH_KEYBOARD_LL)` в observe-режиме. Оба нажимают нормально и в другие приложения.
3. Второе нажатие в пределах окна-детектора (порог ~500 мс) → клиент читает буфер обмена (`tauri-plugin-clipboard-manager`), если он изменился с прошлого чтения → открывает HUD.
4. Если буфер не изменился (второе нажатие — просто повторная копия того же) — не считать запросом.

Обязательные следствия:

- **Разрешение macOS**: event tap требует Accessibility — в спецификацию онбординга входит экран «дай разрешение в System Settings → Privacy → Accessibility» с детектором состояния.
- Глобальный Cmd+C **не регистрируется как hotkey** (иначе сломается вся система копирования); только observe-only мониторинг. Перспективная опция «настроить свой триггер» не включается в MVP — двойной Cmd+C по умолчанию.
- Окно HUD: always-on-top, без таскбара, non-focusable, позиционируется **у курсора мыши** — решение: координаты выделения в произвольном приложении добываются через AX/UI Automation, это ненадёжно и требует пермиссий почти на каждое приложение, а курсор мыши всегда визуально рядом с выделением. Не «таскает» фокус с читаемого приложения.
- **Установка** (решение): локальная сборка `cargo tauri build` — ни подписи, ни notarization, это личный инструмент; автозапуск через `tauri-plugin-autostart`, живёт в трее от логина.

## 5. Модель данных (MVP-1)

В таблицах ниже — поля; всё это SQLite, имена колонок — en-US, документируются прямо в миграциях.

**queries** — каждый вызов HUD, сырой, до и поверх всякой классификации:

- `id`, `created_at`
- `raw_text` — точный текст из буфера
- `kind` — классификация LLM: `word | phrase | sentence | paragraph | fragment`
- `source_app` — приложение, где читали (активное приложение в момент запроса)
- `source_title`, `source_url` — когда доступны (из браузера — заголовок и адрес вкладки; из PDF/IDE — что смогли достать)
- `client` — имя машины (клиент сам себя представит: «work-mac», «home-win»)
- `translation` — JSON ответа HUD (сам перевод, пометки, что вернул LLM)
- `latency_ms` — время от получения текста до отправленного ответа
- `mode` — `instant | soft-revealed` (MVP-1 всегда `instant`, поле закладываем)

**word_entries** — словарный трекинг слов и фраз (`kind in word, phrase`):

- `id`, `canonical` — лемма/нормализованная форма (LLM приводит «went» → «go», «to be about to» как есть)
- `first_query_id`, `created_at`
- `occurrences` — счётчик повторений (наращивается при повторных запросах)
- `last_seen_at`
- `status` — `active | passive` (пассивный список без возвратов — для низкочастотных, появляется в MVP-3)
- `blocked_reason` — для потолка «упрямого» слова (MVP-3)

**query_word_links** — многие-ко-многим: запрос ↔ словарные записи. **Семантика в MVP-1**: связка появляется только у прямых запросов `word|phrase` — перевёл слово, значит сработал трекинг; канонические слова внутри переведённых предложений в MVP-1 не сканируются (второй LLM-проход за латентность не платим), это делается в MVP-2 задним числом по накопленной базе. Сигнал «упрямого слова» в MVP-1 не теряется: он идёт от явных повторных переводов слова. Фраза («to be about to») — **одна** карточка, отдельные карточки её слов не создаются.

**translation_cache** — `canonical`, `lang`, `translation_json`, `updated_at`. Повтор запроса того же слова/фразы — из этой таблицы без LLM. Предложения никогда не кэшируются (контекст всегда живой).

Позже (MVP-2/3, описываю, чтобы схема MVP-1 не блокировала): `constructions` (конструкции дня), `grammar_topics` (грамматическая карта с весами), `review_schedule` (интервальные повторения), `lessons` (сгенерированные уроки), `letters` (письменные задания и ответы).

## 6. Классификация и сигналы

**MVP-1**: классификация работает сразу при поступлении запроса — LLM одним вызовом определяет `kind` и приводит слово/фразу к канонической форме. Правило пограничных случаев — не жёсткий счётчик слов: фрагмент предложения, обрывок, короткая фраза различает LLM; правило PROJECT_CONCEPT «AI, а не счётчик».

**MVP-2 (пополнение задним числом)**: по накопленным `queries` вида `sentence|paragraph` — извлечение кандидатов и построение разборов. Эти поля добавляются к существующим строкам, ни одна сырая запись не переписывается.

Трекинг источников: `source_app/title/url` фиксируются всегда (когда доступны) — из них строится «переводил вчера в доке про Kafka» и группировка по темам. Цели MVP-1 (macOS): **имя приложения — всегда**; браузеры Chrome и Safari — заголовок и URL вкладки (обязаны работать); PDF-ридер и IDE — заголовок окна / имя файла, когда доступны; чаты и терминал — только имя приложения. Windows-цели — те же по возможностям, уточняются при портировании. Если не вытащилось — поле пустое, это норма, не ошибка.

## 7. API (MVP-1)

Версионированный префикс `/v1`, аутентификация — заголовок `X-Api-Token` (токен в env бэкенда, один и тот же для всех клиентов; это защита от случайного соседа в локальной сети, не корпоративная безопасность).

- `POST /v1/query` — `{raw_text, source: {app, title, url}, client}` → `{query_id, kind, canonical (для word/phrase), response (перевод/фраза/разбор — пока только перевод), soft_mode (false в MVP-1)}`. Ответ — **не стриминговый**, одиночный JSON по готовности: слово из кэша — мгновенно, новое — когда LLM ответит (HUD показывает индикатор). Решение о не-стриминге: Ollama живёт локально на одной из машин пользователя, стриминг ради латентности не нужен — если реальность заставит, стриминг добавится как отдельная задача, а не по умолчанию.
- Направление перевода фиксированное: **EN → RU**. Направление в промпт не задаётся как переменная; колонка `lang` в кэше остаётся на будущее.
- `GET /v1/word/{id}/history` — прошлые контексты слова для мягкого HUD и «Разбора» (в MVP-1 не используется, но поле запросов уже позволяет).
- `GET /v1/health` — без токена, для проверки клиентом, что контейнер жив.

Ответы LLM: бэкенд валидирует JSON-схемы ответов модели. Незнакомый формат → ретрай один раз с уточнением, иначе ошибка HUD-у с понятным текстом. Никогда — сырой мусор в базу.

## 8. LLM-задачи

Модель описана как список задач, каждая со своим system-prompt в `backend/prompts/`:

1. **Перевод** — слово/фраза: перевод + короткие пометки (часть речи, регистр употребления). Предложение/абзац: цельный перевод смыслом.
2. **Классификация** (MVP-1) — `kind`, лемма. Объединена с переводом в один вызов: модель отдаёт JSON `{kind, canonical, translation}` — экономим латентность, один запрос на жест.
3. **Разбор** (MVP-2) — предложение по блокам с ролями, связками и грамматической подсказкой (правило 1–3 предложения), извлечение кандидатов.
4. **Урок**: сборка карточек из собственных записей пользователя, генерация продуктивных заданий, проверка писем. (MVP-3.)

Каждая задача — pytest-покрытая функция с валидацией схемы выходов. Промпты — файлы, не inline-строки в коде; правка промпта — правка файла.

## 9. Нефункциональные требования

- **Латентность HUD**: окно появляется < 150 мс после второго нажатия (рисуется сразу с индикатором). Перевод знакомого слова из кэша — < 300 мс на ответ. Новое через LLM — цель 3 с (не жёсткий SLA — модель вращается локально, латентность предсказуема); таймаут бэкенда на LLM — 10 с, дальше понятная ошибка.
- **Таймауты клиента**: ответ бэкенда — 12 с; нет ответа/недоступен — HUD показывает «бэкенд недоступен» и закрывается, запрос в очередь **не** дублируется (жест можно повторить).
- **Приватность**: текст запросов уходит только на собственный Ollama-endpoint и в базу; наружу — только Telegram-сообщения в чат с самим собой. Никакой телеметрии, аналитики, апдейтов «по-тихому».
- **Бэкап**: копия папки `/data` — полный бэкап (SQLite WAL включён, checkpoint при старте).
- **Логи**: бэкенд пишет в stdout (сборит docker), уровень INFO по умолчанию; ошибки LLM-парсинга — WARN с сырым ответом для отладки промптов.
- **One-user повсюду**: никаких пользователей, ролей, мигрений данных между машинами, кроме случая «поднял контейнер в другом месте — указал ту же папку с данными».

## 11. Тестирование

Ключевое требование проекта: **разработку ведёт агент, поэтому всё должно проверяться тестами — от захвата до базы, без человека между шагами.** Подход заимствован у [photocraft](https://github.com/storytold/photocraft) (чистая реализация Photoshop в Rust), где система тестируется насквозь за счёт трёх вещей: «всё — команда» (каждый элемент поведения доступен через командную поверхность, а не только через GUI), оракулы фикстурой (одна реализация служит эталоном для другой) и пиннутые корпусные тесты. Ниже — то же самое применительно к Leng.

### 11.1 Принцип «всё — команда»

- Каждый элемент поведения бэкенда — команда поверх `/v1` (§7). HUD, Telegram-бот и тесты вызывают **одни и те же команды**. Тесты ходят через публичный контракт, а не приватные функции — как это сделал бы настоящий клиент.
- **Клиент тоже имеет headless-поверхность.** Rust-логика клиента (детектор двойного нажатия → буфер → запрос к бэкенду → данные для HUD) живёт в модуле, в который вливаются события, а события может подать кто угодно: ОС — в обычном режиме, тест — через `leng-cli trigger --text "..."` и его CLI-флаги. GUI рисует ровно то, что этот путь вернул, и не содержит собственной логики. Клиентский e2e «событие → бэкенд → базa» тестируется агентом без участия GUI.
- Триггер двойного нажатия — чистая state-машина от потока событий с таймингами, тестируется как функция (`[event] → action`), без ОС.

### 11.2 Пирамида тестов

1. **Юнит-тесты** — Rust (`cargo test`) и Python (`pytest`): state-машина триггера; логика диффа буфера; парсинг и валидация ответов LLM; планировщик интервалов повторения (чистые функции с инъекцией «сегодня»); применение миграций на чистой базе.
2. **Интеграционные API-тесты** — FastAPI `TestClient` поверх реального SQLite во временной папке. LLM заменён детерминированным фейк-клиентом, отвечающим фикстурами из `backend/tests/fixtures/`. Никаких сетевых вызовов ни в одном тесте.
3. **Тесты контракта** — JSON-схемы ответов LLM-задач (§8) и схемы API (§7) пиннуты как файлы; фикстуры валидируются схемой, схема — типами клиента. Клиент и бэкенд физически не могут разойтись незамеченно.
4. **Корпусные тесты** — аналог corpus у photocraft, с пиннингом по sha256: `backend/tests/corpus/` — реальные захваты разных источников и `kind` (слова, фразы, предложения, PDF-обрывки) + эталонные ответы. Меняешь промпт — корпусный дифф показывает, что сдвинулось. Корпус пополняется из живой работы пользователя: обезличенный экспорт из базы — часть мержа MVP-2.
5. **Золотой путь (e2e)** — `docker compose` test-профиль: поднимается бэкенд + фейк-LLM (маленький HTTP-заглушка в контейнере) + временный том. Сценарий headless: word/sentence/phrase-запрос → проверка состояния базы → сдвиг «системного времени» (всё время инъицируется) → генерация урока (MVP-3) → проверка состава карточек. Это и есть тестирование системы от начала до конца.
6. **Telegram-бот** (MVP-3) — mock-транспорт aiogram: уроки и приём ответов прогоняются headless; реальный Telegram — дымовой прогон вручную раз в MVP.
7. **GUI — последний процент.** Никто не автоматизирует клик по HUD и не притворяется, что это надёжно. GUI не содержит логики (§11.1), поэтому ручной чек-лист короткий: хоткей, event tap-права, фокус, позиционирование, ошибка недоступного бэкенда. Меняется GUI — скриншоты «было/стало».

### 11.3 Что тесты не могут и не делают видят

- Поведение event tap / `WH_KEYBOARD_LL` на реальной ОС — не тестируется автоматом, только ручной чек-лист §11.2 п. 7.
- Реальная модель `glm5.3-flash:claude` — не в тестах. Отдельный smoke-сценарий (вручную, не в CI): реальный вызов LLM по корпусу, валидация схем — ловит деградацию промптов/модели между сессиями.

### 11.4 Гейты и команды

- Одна точка: `./scripts/test.sh` — объединённый гейт, CWD-независимый (можно
  запускать из любого каталога). Стадии по порядку:
  1) `pytest` — все тесты бэкенда (в т.ч. golden-, oracle- и purity-тесты);
  2) `ruff check app tests` — линтер Python (правило 5);
  3) `mypy --strict` — на `backend/app/` (правило 5, плагин pydantic.mypy);
  4) `cargo fmt --check` на обоих крейтах клиента (core, src-tauri);
  5) `cargo clippy --all-targets -- -D warnings` на обоих крейтах;
  6) `cargo test` крейта leng-core (tauri-крейт отдельным workspace — тестов нет).
  Выход не нуля = красный; агент не коммитит мимо красного гейта.
- Отдельная стадия после гейта: `./scripts/golden.sh` — golden-path e2e
  (docker compose test-профиль, см. §11.2 п. 5); требует отсутствующего `.env`.
- Опционально GitHub Actions на будущий кол-работы; для личного проекта достаточно локального прогона.
- Definition of done — как в CLAUDE.md §4: критерий успеха сформулирован тестом до кода, тест красный → зелёный. Модуль без теста — не модуль.

### 11.5 Приёмка фичи — чек-лист шести правил

Каждая новая фича (MVP-2/3 и далее) принимается одним и тем же чек-листом
(шаблон из «Шаблон приёмки фичи» дизайна 2026-11-05):

1. Фича = декларация в реестре команд (`backend/app/commands/registry.py`) + валидация
   из её схемы — ни одной ручной кнопки мимо `/v1`.
2. Если у фичи есть оптимизация — наивный оракул в `backend/tests/oracles.py`
   с тестом дельты (прецедент: кэш-оракул «нулевой дельты» для translation_cache).
3. Golden-выход фичи запилен до интеграции, включая минимум один hand-computed
   кейс на MVP (прецедент: `golden_word_hand.json`).
4. Полный `./scripts/test.sh` зелёный (все стадии §11.4).
5. Новое интерактивное состояние доступно headless: через `/v1/state` snapshot
   (правило 6) и/или `leng-cli`; новый рендер — чистая функция с golden-файлом
   (прецедент: `leng-core::render::render_hud_html` + `tests/render.rs`).
6. GUI остаётся без логики; headless-изоляция ядра охраняется тестом
   (`test_headless_purity.py`); ручной чек §11.2 п. 7 — только для того,
   чего headless не может (фокус, хоткей, пермиссии).

Сквозные механизмы, из которых фичи строятся (не «инфраструктура на будущее»,
а текущий источник контрактов): **реестр команд** — единственное место, где
определён HTTP-контракт `/v1` (§7); **оракулы** — эталонные алгоритмы для
тестов эквивалентности; **golden-файлы** (`backend/tests/golden/`,
`client/core/tests/`) — пиннутые выводы генераций и рендера; **гейт-стадии**
§11.4 — обязательная приёмка каждого коммита.

## 12. Разработка

- **Test-first** по CLAUDE.md: RED → GREEN → REFACTOR для каждого модуля (см. §11.4).
- **Команды** (реальные, на диске после MVP-1):
  - `./scripts/test.sh` — весь гейт одной командой (бэкенд: pytest + ruff +
    mypy --strict; клиент: fmt + clippy + cargo test крейта leng-core).
    mypy/ruff/clippy отдельными ручными командами не вызываются — только
    стадии гейта. CWD-независимый.
  - `./scripts/golden.sh` — golden-path e2e бэкенда: сборка образа, compose-профиль test (бэкенд + fake-llm), word-запрос, проверка SQLite; hermetic, требует отсутствующего `.env` в корне.
  - `docker compose up -d` (боевой бэкенд, конфиг из `.env`; реальная модель задаётся `LENG_LLM_MODEL` — дефолт в config.py).
  - Клиент: `cargo build` из `client/src-tauri` (tauri-CLI не нужен), запуск: `LENG_BACKEND_URL=... LENG_API_TOKEN=... target/debug/leng`.
  - Headless: `leng-cli trigger --text "..." --base-url http://... --token ...` (бинарник из крейта leng-core, тот же пайплайн, что в GUI).
  - `leng-cli snapshot` НЕ реализован: правило 6 («состояние читается без GUI»)
    уже покрыто `/v1/state` (§7). Headless-дамп состояния клиента средствами
    CLI откладывается до MVP-2, когда появится состояние, не видимое бэкенду.
- **Языки**: код, комментарии, имена — en-US; документация (этот файл и будущие под docs/) — по-русски.
- **Ручной чек-лист §11.2 п. 7 (MVP-1, macOS) — пройден на живом прогоне 2026-11-04**: двойной ⌘C → HUD у курсора, открывается мгновенно, до ответа — спиннер; перевод виден в Chrome (записаны `source_title`/`source_url` вкладки); «бэкенд недоступен» с причиной при выключенном контейнере. Атрибуция источников: Chrome — вкладка (title+URL), Terminal — заголовок окна через AX, Preview (PDF, «leng-ax-check.pdf – 1 page») — заголовок окна через AX; Preview/Terminal проверены выводом `source_info()` на живых окнах (временный отладочный прогоночник, удалён), Chrome — принятым запросом живого приложения. Отмена HUD (Escape на живом прогоне) при летящем запросе не воскрешает окно: payload после отмены отбрасывается (supersede-правило генераций). Записи источников в `/data` (sqlite3) проверены на первом прогоне, до AX-пути.
- **Изменения поведения HUD/захвата** проверяются вручную по чек-листу §11.2 п. 7 на обеих ОС перед мержем (права, event tap, WH_KEYBOARD_LL — то, что в тесте не проверить).

## 13. Вне проекта (по PROJECT_CONCEPT.md)

Не курс (нет программы уровней), не замена словарю, не тренажёр с расписанием, не продукт для всех, без геймификации. Технически это означает: никакой многопользовательности, никаких стриков/достижений в схеме, никакого внешнего учебного корпуса — уроки собираются только из записей пользователя.
